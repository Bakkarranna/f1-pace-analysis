# f1-pace-analysis — race pace, stints and tyre age

**Level 1 of the Formula 1 data portfolio.** Pure data fundamentals: take a real
race dataset and answer, with numbers, the three questions a race engineer asks
about pace.

1. **Which driver had the strongest pace over a stint?**
2. **How does lap time change as tyre age increases?**
3. **How does pace change before and after a pit stop?**

Everything here is measured from real timing data, not asserted. Every number in
the report below is regenerated by `f1pace report` from the CSVs that ship in
[data/processed](data/processed), and the counts come from the repository's own
output — no hand-typed figures.

## What it measures

| Question | Method | Output |
|---|---|---|
| Strongest stint pace | Trailing 3-lap rolling average, normalised to the driver's own stint median | ranked stint table per race |
| Tyre degradation | OLS of lap time on tyre age **with a fuel term** | s/lap-of-age with a 95% CI |
| Pit stop effect | Normalised pace 3 laps before vs 3 laps after each stop | pooled before/after delta |

### Why the fuel term is not optional

A car gets lighter as a race runs, so it gets faster. Tyre degradation makes it
slower. Fit one without the other and you get the wrong answer: ignoring fuel
understates degradation, because the lap-time trend you attribute to tyres is
partly just a shrinking fuel load. [degradation.py](src/f1pace/degradation.py)
fits `lap_duration ~ tyre_age + fuel_laps_remaining` and reports the slope with
a confidence interval, so a slope that overlaps zero is reported as zero rather
than rounded into a story.

### Which laps are kept

[ filters.py ](src/f1pace/filters.py) drops, in order and with attributable
counts: the formation lap, pit-out laps (cold tyres), in-laps (driver already
saving the car), laps under yellow or safety car, race lap 1 (traffic-dominated
standing start), laps with no tyre age, and laps slower than 105% of the
driver's own median. The `summary()` helper replays the rules one at a time so
the report can say *which* rule removed how many laps, instead of one
unexplained `raw - clean`.

## Data

Four 2024 Grands Prix chosen for contrast, fetched from the
[OpenF1](https://openf1.org) REST API by [fetch_openf1.py](scripts/fetch_openf1.py):

| Race | Session key | Character |
|---|---|---|
| Bahrain | 9472 | abrasive surface, high degradation |
| Monaco | 9523 | low-speed, maximum downforce, tyres the limit |
| Monza | 9590 | fastest lap of the season, low degradation |
| Singapore | 9606 | street circuit, ~half a lap off the leaders |

Flag state comes from the same API's `race_control` feed
([fetch_flags.py](scripts/fetch_flags.py)) rather than being inferred from lap
times, so neutralisation is measured, not guessed.

## Reproduce

```bash
pip install -e ".[dev]"

# offline: use the CSVs that ship with the repo
f1pace report                     # writes reports/RESULTS.md
f1pace stats                      # laps kept/lost per race, with the reasons
f1pace stints --races monaco      # strongest stints at one race

# refresh from source
python scripts/fetch_openf1.py
python scripts/fetch_flags.py
f1pace report
```

## Tests

```bash
pytest -q        # filters, degradation, stints, pit stops, and the data contract
ruff check .
```

`tests/test_real_data.py` is a data contract: it fails if the fetch script ever
produces a table missing `tyre_age`, with duplicate `(driver, lap)` rows, fewer
than 15 classified drivers, or a tyre age that does not restart at each stop.
